It keeps start, execs, pulls, and stop in one process. Always give it your own unique `scan_id`; never use it to inspect another process's sandbox.

### Process and lifecycle invariants

- `scan_id` is only an in-process key in `_SESSION_CACHE`; it is not a Docker container name, label, or cross-process rendezvous point.
- Two independent MCP server processes using the same `scan_id` create separate containers and separate Caido instances. Use one server process with the supported commander/child model, or intentionally assign distinct `scan_id` values.
- A normal server exit runs cleanup. If the process or Docker engine is killed first, orphaned containers can remain. Inspect with `sandbox_status` and cross-check host `docker ps -a`; `sandbox_reap` is not a complete cleanup guarantee.
- Pull evidence out of `/workspace` before stopping. `sandbox_stop` deletes the container and its writable layer.

### Codex plugin bridge (preferred)

The Codex-native tools are provided by the local plugin `strix-sandbox@strix-local`, not by a standalone `mcp_servers` entry. The plugin manifest is at `C:\Users\Administrator\.codex\plugins\strix-local\plugins\strix-sandbox\.codex-plugin\plugin.json`; its MCP configuration is in the adjacent `.mcp.json`.

The facade runs under the Strix MCP virtual environment:

```text
D:\code\work\strix-main\.venv-mcp\Scripts\python.exe
D:\code\work\strix-main\qoder_mcp\strix_sandbox_fast_mcp.py
```

The real server remains `strix_sandbox_mcp.py`. The facade answers `initialize` and `tools/list` using only the Python standard library, then lazily starts the real server on the first tool call. This avoids Codex's catalog race: the real server takes about 3.5 seconds to import Strix, Docker, and Caido, while the facade reaches ready in about 0.2 seconds.

The plugin `.mcp.json` must keep:

```json
"omit_tools_from": ["code_mode", "deferred"]
```

Without that setting Codex can list the server and tools while leaving the model-side router without the callable tools. A plugin install or configuration change takes effect in a new Codex thread; the current thread may retain its old tool catalog until the app restarts.

The plugin exposes the 12 tools with server name `strix_sandbox`. A model-facing call uses the plugin's normal MCP naming, for example `mcp__strix_sandbox__sandbox_status`; the router's exact model name is resolved by the plugin catalog, not by the stdio client.

## MCP timeout and file-read recovery (verified 2026-10-26)

- `sandbox_exec.timeout` is **seconds**, not milliseconds. The MCP bridge clamps it to at most 300 seconds. Start longer scans detached (`setsid ... >/workspace/log 2>&1 </dev/null &`) and poll the log.
- `sandbox_read_file` now defaults to 20 seconds and is hard-capped at 60 seconds. It reads through a bounded `cat`; it no longer calls the SDK's unbounded `read()` path.
- The fast MCP facade has its own response timeout (read: caller timeout + 10 seconds, exec: command timeout + 15 seconds) and sends `notifications/cancelled` when a response is late. The Codex plugin ceiling is 360 seconds.
- If a read still times out, do **not** retry it. Check `sandbox_status`, then use `sandbox_exec` for `wc/head/sed`, or the host fallback:
  - `docker cp <container_id>:/workspace/<path> <host_path>`
  - `docker exec <container_id> sh -lc 'wc -c /workspace/<path>; head -n 120 /workspace/<path>'`
- Windows stdio is forced to UTF-8 (`PYTHONUTF8=1`, `PYTHONIOENCODING=utf-8`), and bridge JSON is ASCII-escaped to avoid GBK codec failures on Chinese Markdown or symbols such as `░`.
## Top reminders (read first — re-verified 2026-10-15, image `03d9e33a00d8`)

- **`sandbox_stop` DELETES the container** — it is not a pause. The container is removed and the next `sandbox_start` binds a **fresh** container id with an **empty `/workspace`**. Pull every artifact out before stopping.
- **Replays: always pass a full `url`.** A `path`-only modification now stalls ~30 s and returns `status=ERROR` / `response_raw=null` — it is no longer "silently ignored" (see Traffic & Caido rules).
- **`sandbox_reap` is not a cleanup safety net** — it returns 0 candidates for containers built from a now-dangling image id. Stale containers need host-side `docker rm`.
- **`sandbox_write_file` creates missing parent dirs itself**; `mkdir -p` is only needed for writes issued through `sandbox_exec`.
- **Re-verify tool presence with `command -v` before depending on it** — availability is per-container, and the image content changes between builds (dalfox moved *into* the image since 2026-10-09).
- Shared-container browsers: **always** `agent-browser --session <name>` on every command, and **close it when done**. Budget **~12–15 procs / ~1.2 GB RSS per session** (MCP's internal trip-wire is **16 procs / 1500 MB**); the old 340 MB figure was wrong. Every `sandbox_exec` whose command contains `agent-browser` echoes `browser: {procs, rss_mb}` — **read that number**, and if you get a `browser_hint`, close your session before doing anything else.

## Core usage

- Default shared sandbox: `scan_id="qoder"`. Check `sandbox_status` first; `sandbox_start` only if none running.
- Every in-container tool runs through `sandbox_exec` (nmap, sqlmap, nuclei, ffuf, katana, semgrep, python3, curl/wget, git, `agent-browser`). Non-interactive flags + generous `timeout` (sqlmap: `--batch --level 1 --risk 1`; nmap long scans: minutes).
- Files: `sandbox_read_file`/`sandbox_write_file` are UTF-8 text only **and accept only paths relative to `/workspace`** — an absolute path elsewhere errors with "manifest path must be relative"; use `sandbox_exec("cat ...")` instead. For binary out of the container: `sandbox_exec("base64 <file>")` then decode host-side (verified 2026-10-15: `head -c 24 /bin/ls | base64 -w0` round-tripped the ELF magic `f0VMRg…`). ⚠ **Corrected 2026-10-15: `sandbox_write_file` creates missing parent dirs itself** — writing `/workspace/selftest/hello.txt` when `selftest/` did not exist succeeded (62 bytes, UTF-8 Chinese intact). The old "writes need existing parent dirs" rule was wrong; `mkdir -p` is only needed for writes issued via `sandbox_exec`.
- Proxy chain order for web work: generate traffic (curl/agent-browser via `sandbox_exec`) → `proxy_list_requests` (HTTPQL filter e.g. `req.host.cont:"x" AND resp.code.gte:400`) → `proxy_view_request` → `proxy_repeat_request` (modifications dict: **use a full `url` — a `path`-only change stalls 30 s and errors**; `headers` replaces the block, so resend `Host`/`User-Agent`; never run two repeats in parallel) → `proxy_list_sitemap`.

## Installing or refreshing tooling (egress is intercepted)

- Unset `http_proxy`/`https_proxy` first; they point at Caido `127.0.0.1:48080` and break package fetches.
- Plain HTTP:80 is hijacked by a middlebox (answers 502). `http.kali.org` redirects to a dead mirror (`kali.cs.nycu.edu.tw`, SSL-truncated) — set `URIs: https://mirrors.tuna.tsinghua.edu.cn/kali/` in `/etc/apt/sources.list.d/kali.sources` and install with `-o Acquire::http::Proxy=false -o Acquire::https::Proxy=false`. (aliyun and ustc mirrors also work.)
- Reachable: github.com, raw.githubusercontent.com, codeload.github.com, pypi.org, proxy.golang.org. `api.github.com` is 60 req/h on a shared IP and **will run out** — never script release lookups against it.
- `nuclei -update-templates` silently fails here: the process goes defunct, the log holds only the banner, and the template dir is untouched. Working method: fetch `https://codeload.github.com/projectdiscovery/nuclei-templates/tar.gz/refs/tags/v<ver>`, extract, swap `~/.local/nuclei-templates` (keep a `.bak`). `-ntv/-new-templates-version` does **not** filter on a tar-installed tree — it lists everything, so keep your own template-list baseline.
- If a download suddenly returns `500` with a ~9 KB HTML body (seen on raw.githubusercontent.com after an engine restart), decide who is lying by fetching the same URL twice — once through Caido, once with the proxy unset. **Identical status AND identical `size_download` = the host egress path is serving you an error page**, not Caido flake and usually not GitHub (its status page said all-operational at the time). Retry later or use a different artifact source.
- `dalfox` flags (re-verified 2026-10-15, dalfox now present in-image): `dalfox --version` → `Error: unknown flag: --version`; `timeout 8 dalfox version` prints the banner and exits 0 — **no hang**. Historical context kept on purpose: the hanging-`version`-flag trap was only ever observed in containers where dalfox had been apt-installed into that container's own overlay. Dalfox also ships `mcp` (stdio MCP server) and `server` subcommands.

## Shell traps (caused repeated exit-143 self-kills)

- NEVER `pkill -f <pattern>` / `pgrep -f <pattern>` where the pattern string appears in the command itself — the wrapping `sh -lc` matches and kills itself (exit 143, remaining commands skipped). Instead: capture the PID (`cmd & pid=$!; ... kill $pid`) or break the literal with a character class (`889[9]`). Heredoc variant (2026-10-08, worker w65160): a command that *writes* the pattern into a file (`cat > loop.sh <<'EOF' … for h in …`) self-matched its own `ps|grep` kill loop — the heredoc text is part of the wrapping shell's cmdline, so the char-class trick inside the grep does not protect. Safe workarounds that worked: build the pattern dynamically (`pat="for"" h in"` + `awk -v p="$pat" 'index($0,p)'`), and prefer `sandbox_write_file` (relative `/workspace` path) to materialize scripts — the script's own cmdline is then just its path.
- Background servers: launch detached and reliably: `setsid <server> >/tmp/x.log 2>&1 < /dev/null & hp=$!` then `sleep 1-3` before use; kill by `$hp` later. Plain `(nohup ... &)` gets reaped with the exec shell. Re-confirmed 2026-10-15: `setsid sh -c 'sleep 20; echo done > /workspace/selftest/detached.txt' >/dev/null 2>&1 < /dev/null &` returned instantly and the file landed exactly 20 s later, with the exec channel still responsive in between — this is the pattern for anything that outlives a single call. Poll cheaply (`cat <file>; date +%s`), and use `ps -o pid,rss,cmd -C python3 --no-headers` / `ss -tln` to confirm a listener is still up before replaying against it.
- Long installs/scans: the MCP call itself dies at ~120-200s wall clock with "MCP tool invocation did not complete", **but the command keeps running in the container**. Launch with `setsid ... >/workspace/x.log 2>&1 < /dev/null &` and check the log/PID in later short calls. Never re-issue the same heavy command because the first "failed" — you will end up with two.
- A kill that returns 143 may still have done the work — re-verify with a fresh exec (`ss -tln`, `ls`) instead of assuming failure.
- `sandbox_status` now cross-checks every cached bundle against the Docker daemon: it reports `container_state` (ground truth) and `stale:true` when the in-process cache outlived the container. `sandbox_start` self-heals: running cache reused, exited/created/paused container **revived in place** (writable layer preserved — verified), unrecoverable/absent purged and recreated. `sandbox_exec` failures annotate `container_state` in a `hint`. Residual truth-check: a light `echo alive` (daemon "running" can still wedge its exec channel).
- `sandbox_reap(confirm=true)` over many strays (20+ overlay layers) tends to just **block**: the call times out and the removals may never happen. Never report cleanup as done — re-check with `docker ps -aq | wc -l` from the host. It also can't be distinguished from a wedged daemon while it's queued.
- ⚠ **`sandbox_reap` also CANNOT SEE containers built from an older, now-untagged image of the same name** (verified 2026-10-15) — so a clean dry run does **not** mean the host is clean. Evidence: the host held **13** stale containers (mostly `Exited (137)`, two `Created`) whose `Config.Image` still read `ghcr.io/usestrix/strix-sandbox:1.3.0` but whose image id `f6906c3114e5` had gone **dangling** (`RepoTags: []`), while the live image id was `03d9e33a00d8`. `sandbox_reap(confirm=false)` returned `{"candidates": [], "removed": []}`. **Always cross-check host `docker ps -a` and remove such strays with host-side `docker rm`** — never assume reap covered them, and never claim cleanup was done off the back of an empty candidate list.
- After a Docker engine restart, an Exited-but-present container is now revived automatically by `sandbox_start` (same container id, exec probe, layers kept: installed tools/wordlists/templates survive — check before rebuilding anything). Manual host-side `docker start <id>` remains the fallback if revive fails.
- **`sandbox_start` can also die at the Docker-API layer with a 60 s read timeout while creating *nothing*** (verified 2026-10-09, interactive `scan_id="qoder"`): the call returns `NpipeHTTPConnectionPool(host='localhost', port=None): Read timed out. (read timeout=60)`, then `sandbox_status` still reports `{"running":[],"count":0}` and host `docker ps -a` is **unchanged**. This is the opposite of the "container created but never registered" signature in Multi-agent discipline — here no container exists, so there is nothing to clean up. **Just call `sandbox_start` again; it succeeds and binds a fresh container id.** Always check host `docker ps -a` before deciding which of the two signatures you hit, and never report a sandbox as running off the back of a timed-out start.
- A foreground-ish call that actually runs ~100s+ in-container (e.g. a `for` loop of `curl -m 10` over 15 hosts, or `sleep 90` inside the command) can **wedge the exec channel of that worker's own container**: every later `sandbox_exec`/`sandbox_read_file` returns "exec transport error", `sandbox_start` (idempotent re-handshake) still reports the old container, and only `sandbox_stop` succeeds. There is no recovery — pull what you can from your own transcript before stopping, and keep each call to `setsid <job> &` + short polls (`cat state; wc -l out`). Never plan a phase around one long blocking call. ⚠ **But do not over-apply this** (verified 2026-10-12, interactive container): after an MCP-layer abandonment (`-32603`) of a long call, the next `echo alive` may return `"command timed out"` — a **different, recoverable** signature. Retry the light probe before declaring the channel wedged.
- Flag reality in image 1.3.0 (verified 2026-10-07): `nuclei v3.11.0` has **no `-d`/`-delay`** (use `-rl 1 -rld 1s`) and `-json` must be `-j` (`-json` = "flag not defined"); `-tl` is *template listing*, feed a directory to `-t` (no `rsync` in image — materialize a subset with `tar -cf - -T rel.txt | tar -xf - -C dir`). `ffuf v2.1.0-dev` has **no `-delay`** (use `-p <sec> -t 1`). `katana` has no `-fo`; output format is implicit with `-o`, and `-kf` takes a **single** value (`all`|`robotstxt`|`sitemapxml`, comma list = abort). `subfinder` has no `-d-list`; pass `-d dom1,dom2`. `httpx` uses `-rl` (rate-limit) **not** `-rate`, and `-rate` aborts with usage printed to stdout (invisible if you discard stdout). Also on `nuclei v3.11.0`: **`-no-update-templates`, `-nf` and `-d` are all "flag provided but not defined"** — template scoping is **only** honoured via `-ud <staged-dir> -duc` — `-t`/`-nt`/`-tl`/`-id` were all measured **inert** for scoping in image 1.3.0 (six probes, each printing the same template count; verified 2026-10-10 w65064) ⇒ stage the subset into your own dir and point `-ud` at it, and skipping the auto-update is unnecessary since it never fires without `-update-templates`. **Budget nuclei per group, and only a group that prints `END` counts as covered** (one group = 2248 templates is not one run; verified 2026-10-10 w65050). A run of 1187 templates at `-rl 1` is ~20 min: launch detached + poll the `-o` file, don't wait on the call (`Templates clustered: N` in the log is the only progress signal; `-o` output file is created at start and stays 0 bytes while clean).
- **`katana -delay` takes SECONDS (duration), not ms** (verified 2026-10-09, worker w65081): `-delay 2000` means one request per 2000 s, so the crawl still looks alive (`portal.txt` 0 bytes, process running) for hours while sending ~nothing — use `-rl 1` alone, or `-delay 2s`. **Always scope katana's crawl to the target**: worker w65075 (2026-10-09) ran `-d 2 -rl 1` without domain scoping and fetched **8 distinct out-of-scope external URLs** (self-reported, listed in `raw/oos_w65075.txt`) — add `-cs rdn` (crawl scope = root domain), and register the out-of-scope list as a deviation if it happens. ⚠ **`-fs` is NOT a scope filter** — it is the OUTPUT FIELD selector (`-fs fqdn` only changes what gets printed, it does not restrict the crawl; verified 2026-10-12 with two measured failures). Also `katana v1.7.0` in this image **intermittently emits only the input URL** (`Crawl completed … 1 endpoints found` across six flag combinations, verified 2026-10-10 w65061/w64952) ⇒ treat a 1-endpoint crawl as a **tool failure, not as "no links"**, and fall back to parsing the page HTML for `href/src/action`. Run `katana -h` before relying on any flag. Same worker also confirmed the mid-session MCP tool-set re-attachment path: the session started with `mcp_list {keyword:"strix"}` → 0 tools (host-side stdio driver used instead), then the 12 `mcp__strix_sandbox__*` tools appeared mid-run after the operator reopened Docker; the IDE-side `sandbox_status` registry is separate from a host-side driver's, so a container created by one is invisible (`{"running":[],"count":0}`) to the other — always confirm ownership via the host `docker ps` before assuming a container is gone.

## Traffic & Caido rules

- `NO_PROXY=localhost,127.0.0.1`: loopback traffic is NOT captured. To produce capturable traffic bind listeners on `0.0.0.0` and hit the container IP from `hostname -i`, or hit a real external host. Re-confirmed 2026-10-15: `curl -s -o /dev/null -w 'ip=%{remote_ip}'` returns `127.0.0.1` for every egress request (proof the container's Caido is in the path); a listener on `0.0.0.0:8099` hit via `127.0.0.1` was invisible to Caido, while the same listener hit via `172.17.0.2:8099` was captured as a normal entry. Useful HTTPQL forms that work as written: `req.host.cont:"example.com" AND resp.code.eq:404`, `req.host.cont:"172.17.0.2"`, `req.raw.cont:"X-Replayed"`.
- `proxy_repeat_request` requires the target still listening at replay time. Keep the test server alive until after the repeat; only then kill it (container stop also kills everything).
- ⚠ **`modifications` honours `url` and `headers`; a `path`-only modification now FAILS — the earlier "silently ignores `path`" behaviour no longer holds** (updated 2026-10-15). Verified in a fresh container: replaying a captured `GET http://172.17.0.2:8099/hi.txt` with `{"path":"/nonexistent-xyz.txt"}` stalled **twice, 30 071 ms and 30 052 ms**, and returned `{"status":"ERROR","error":"Caido replay dispatch did not complete within 30s …","response_raw":null}` — while `{"url":"http://172.17.0.2:8099/hi.txt","headers":{"Host":"172.17.0.2:8099","User-Agent":"curl/8.20.0"}}` completed in **299 ms** with `200` and the file body. **Rule: always pass a full `url` (scheme+host+port+path) for any rewrite; never rely on `path` — it burns 30 s and returns nothing.** (Historical 2026-10-09 note: back then the same `path`-only replay returned the *original* path's response byte-for-byte, so a "successful" replay whose response is byte-identical to the original was the tell — either way `path` never rewrote anything.)
- `modifications.headers` **replaces the header block wholesale** (verified 2026-10-09): passing only `{"X-Replayed":"yes"}` drops `User-Agent`. Pass `Host` and `User-Agent` explicitly alongside any header you add.
- **Never fire two `proxy_repeat_request` calls in parallel** (verified 2026-10-09): with two in flight, one failed with `proxy call failed: A network error occured / Transport is already connected`. Serialize repeats.
- Replays are themselves **captured by Caido as new entries** — don't trust the returned response alone, confirm what actually went on the wire. HTTPQL matches raw bytes too: `req.raw.cont:"X-Replayed"` finds an injected header, `req.path.cont:"hello"` confirms (or refutes) a path rewrite.
- `proxy_list_sitemap` takes `scope_id / parent_id / depth / page / page_size` only (no `first`/`sort_by`/`httpql_filter`) — passing request-listing params errors with `must NOT have additional properties`. Drill the tree by `parent_id`.
- External targets through Caido occasionally return upstream 500 — that is flake, not a bug. For deterministic verification use an in-container listener; retry externals once before concluding. Tell for Caido's *own* error pages (hit 3× on 2026-10-08): the body carries `<title>Caido` and curl's `-w` shows `ip:127.0.0.1` — seen as 400 for non-80/443 ports (e.g. `:1113`) and as 502 shells; that is NOT the target's response, re-probe with `--noproxy '*'` and compare `size_download`.
- Browser→proxy cross-validation: `agent-browser open <url>` (it inherits `http_proxy`) then `proxy_list_requests` filtered by host — proves capture and gives raw request/response.
- `proxy_list_requests` returns whole raw request+response blocks and **ignores `limit` (and often narrows poorly)** — a host filter on a browsed site easily exceeds the 25k-token MCP cap and lands in a tmp file; grep that file (`set-cookie|x-frame-options|strict-transport` with `-o`) instead of re-listing. Header forensics is usually cheaper with direct `curl -D -` on paths that bypass the target's front-end.
- `/opt/strix-python/caido_api.py` is **async**: `await list_requests(...)`, `await view_request(id, part='response')`; calling without `asyncio.run` returns a coroutine (or a `Connection`) and JSON-dumping it throws. Signature: `list_requests(*, httpql_filter=None, first=50, after=None, sort_by, sort_order, scope_id=None)`.
- ⚠ **nuclei traffic is NOT captured by Caido** (verified 2026-10-10 w65061): nuclei's fastdialer dials the origin **directly** and ignores `HTTPS_PROXY` ⇒ **never use proxy request counts as nuclei coverage or hit evidence**. Measure coverage from nuclei's own `-stats` / the group's `END` line, not from Caido.
- ⚠ **Caido fabricates `502` + `<title>Caido</title>` (8960–9133 B) for hostnames that do not resolve** (verified 2026-10-10 w65064: 11 of 21 probed apex hosts "returned" it). So a Caido 502 is **not** target evidence and **not** a liveness verdict — re-probe with `--noproxy '*'` before concluding anything about a host being down.
- ⚠ **DoH/CT lookups are dead inside the container** (verified 2026-10-10 w65046): DNS-over-HTTPS from in-container resolves **through Caido** and comes back as the Caido error page ⇒ do DoH/CT/crt.sh work **host-side**, not in the sandbox.
- ⚠ **ProjectDiscovery tools phone home to `api.pdtm.sh` even with update-check disabled** (verified 2026-10-10 w65046): nuclei/subfinder/katana each emitted telemetry GETs carrying the target/scan id. Register it as third-party egress in the deviation log; it is not target traffic and must never be counted as such.
- ⚠ **nuclei `http/osint` / `rdap-whois` family autonomously queries third-party registries** (verified 2026-10-11 w65022: staging that directory produced 11 `rdap-whois` requests to registrars) ⇒ **exclude those templates before staging** a run, or you generate out-of-scope egress on the target's behalf.
- ⚠ **`-rl 1` is NOT 1 request/second when the target keeps the connection alive** (verified 2026-10-11 w65012 / 2026-10-12 w64996 / 2026-10-14 w64952): a group "at `-rl 1`" measured **RPS 76 / 51**. The **decision window is the FIRST `-stats` line**, not a later spot-check — read it and stop if the measured rate is not what you declared.
- **Identify a container's owner by `.Mounts[].Source`, never by `HostConfig.Binds`** (verified 2026-10-11 w65001): a worker declared a still-running container "not mine" off the wrong field. Use `docker inspect -f '{{json .Mounts}}' <cid>` to prove identity before touching anything.

## Multi-agent discipline (commander mode)

- Parallel workers get **their own container**: `scan_id="w<target-id>"`. Each worker calls `sandbox_start` for its own scan_id at task start and MUST `sandbox_stop` at exit — hard isolation kills /tmp cross-talk, shared Caido history, and browser-session stomping at once. NEVER call `sandbox_reap`, never touch another scan_id. If a worker died and left its container (crash residue), only stop that specific `w<id>` after confirming no worker is live.
- Shared `scan_id="qoder"` is for interactive/single-agent work; in that mode lifecycle belongs to the commander and agents must not start/stop.
- **Engine outage is shared state — a worker must never restart it.** When `sandbox_start` fails with `500 Server Error for http+docker://...` (Docker Desktop Linux engine wedged; host `docker version` also 500), restarting the engine kills every concurrent worker's container mid-run. Correct degradation: keep doing P1 passive attribution, fall back to manual single-request HTTP/HTTPS forensics from wherever still works, and otherwise record the blocked phases as `open_proof_gap` and close out. Engine restart is the operator's decision, made when no worker is in flight (observed 2026-10-07: one worker restarted it under approval and cost two concurrent workers their run). **Second signature** (observed 2026-10-08, worker w65160, containers mid-run): ALL `mcp__strix_sandbox__*` calls — including `sandbox_status`, `sandbox_write_file`, `sandbox_stop` and a bare `echo alive` exec — time out with `-32603 MCP tool invocation did not complete`, while host `docker version`/`docker ps` hangs with zero output. Distinguish from the exec-channel wedge (there `sandbox_stop` still succeeds; here nothing does). No worker-side recovery: record `sandbox_stop 未确认` + container_id in SUMMARY, leave cleanup (`docker stop <id>`) to the operator, do not retry in a loop. Follow-up evidence (same incident, ~20 min later): host `docker version` finally returned `failed to connect to the docker API at npipe:////./pipe/dockerDesktopLinuxEngine … cannot find the file specified` — the Docker Desktop Linux engine daemon had fully stopped (Linux containers die with it), and a re-probe still hung before erroring (the CLI does not fail fast — never loop it). Under this signature the practical end-state is "container already down with the engine"; still record it and flag possible Exited metadata for operator cleanup after an engine revive. **Commander rule** (2026-10-08, same incident): while this signature is live, `sandbox_status` itself fails, so container-housekeeping is impossible — **stop dispatching new targets** (a new worker can only run host-side degraded and will close with P2/P3/P4 gaps, i.e. it burns a slot to produce a half-run), keep collecting whatever already reached disk, and re-probe `sandbox_status` once per tick until the engine answers again. **Third signature — MCP server wedged while Docker is healthy** (2026-10-08 20:44, worker w65132 then commander): every `mcp__strix_sandbox__*` call returns `-32603`, yet host `docker ps` / `docker version` answer instantly and a container is genuinely `Up`. Cause is the stdio server itself (one connection, blocked after a long call the MCP layer abandoned), not the daemon — so **do not restart Docker** (it is fine and a restart would kill the live container); the fix is reloading/redisabling the MCP server by the operator. Two consequences: ① a worker must never conclude "my container is gone" from `-32603` — record `sandbox_stop 未确认` + container_id and let the commander/operator verify after reload; ② while wedged, sibling workers keep running and degrade to host-side forensics, so still do not dispatch new targets. **Worker-side symptom may be harsher than a timeout**: the wedged server can disappear from the session's tool set entirely (`mcp_list {keyword:"strix"}` → `{"tools":[],"total":0}`). Then never fake a container lifecycle — do not `sandbox_start`, do not invent a `sandbox_stop` return value; write in SUMMARY 「未启动容器 / 无 sandbox_stop 返回值可写（MCP 不在工具集）」 plus the host-side fallback actually used, and mark container-dependent phases `open_proof_gap`.
- Sub-agents don't inherit your context: embed exact knowledge-pack file paths (see strix-pentest-knowledge) and current target/creds into each worker prompt.
- **`sandbox_start` can time out at the MCP layer ("MCP tool invocation did not complete") while the container is actually created and `Up`** — the server's session cache never registers it, so the next `sandbox_status`/`sandbox_exec` answers "Sandbox 'w<id>' is not running. Call sandbox_start first." while `docker ps` shows it running. Fix: just retry `sandbox_start` (idempotent) — it binds a **new** container id and work proceeds normally; the first container stays behind as same-scan orphan. Stop that orphan specifically with host-side `docker stop <id>` (keep it, don't `rm`) and record it in the deliverable — do NOT `sandbox_reap`, and confirm identity first (`PYTHONPATH=/opt/strix-python` inside it + creation timestamp matching your own call).
- **浏览器史实（别被旧笔记误导）**：2026-10-11 曾有「**禁用 `agent-browser`**」的临时红线——起因是 worker w65001 每看一页就开一个浏览器，宿主 `docker top` 聚合到 **55 个 chromium ≈ 5.5 GB RSS**（容器 VM 只有 3.75 GiB），差点把自己的 nuclei/P2 挤爆。**该红线已于 2026-10-12 解除**：根因是 agent 侧的 session churn（每条命令都新开、而不是复用），不是工具本身；服务端同日加了 `browser_procs`/`browser_rss_mb` 回显。所以现在的口径是「**固定 session 复用 ＋ 收工前看 `browser_procs`**」，而不是「禁用」。
- **真实数字与 churn 成因（2026-10-12 实测 w64976）**：一个 `agent-browser` 会话 = **13 个 `chromium` + 2 个 `chrome_crashpad` ≈ 15 个活进程 / ~1 295 MB RSS**（`docker stats` 因共享页会显示更少）。三条 churn 成因：① **3 分钟 idle 回收 vs AI 回合节奏** —— 间隔 >3 分钟就冷启动，所以**把浏览器操作批量放进一次调用**，别一条命令开一次；② **混用默认会话 / 中途改名** —— 每个不同 session 名 = 多一整个浏览器（≈11 procs / 340 MB）；③ **`close --all` 会漏** —— 约 8 个 chromium 子进程能活过 close，反复开关会累积。⇒ **整个任务保持一个浏览器热着，最后只 close 一次，别每页 close。**
- **Governor 规则**：**一个容器只用一个具名会话，绝不开第二个**；自己容器若 `browser_rss_mb ≳1500` 或 census 显示 >16 个浏览器进程而你确信已关 ⇒ `agent-browser --session <你自己的名字> close` 再复核（实测一次成功的 close 确实释放进程）；**长 nuclei/扫描阶段不要挂着浏览器**——扫描前 close、P6 再开；容器 stop 是最后手段且只对自己的 `scan_id`。手动 census（服务端回显不可用时）：`ps -eo comm=,stat=,rss= | awk '$2 !~ /Z/ && $1 ~ /^(chromium|chrome)/ {n++; r+=$3} END{print "live_procs=" n+0, "rss_mb=" int(r/1024)}'`。
- Inside any SHARED container, browsers need per-agent `agent-browser --session <worker-name>` on EVERY command (default session is shared and stomped); close when done (idle 3min auto-reclaim). ⚠ **Measured 2026-10-15: one session peaked at 12 chrome processes / 981 MB RSS**; the MCP's own trip-wire is **16 procs / 1500 MB**, and the server's comment records a session as **12–15 procs / ~1.2 GB** ⇒ **budget ~1.2 GB per session, not 340 MB**. `agent-browser --session <name> close` dropped it to 0 MB with 3 residual procs. Useful smoke test: `agent-browser --session X open https://example.com` then `agent-browser --session X get title`.
- **进程数回显是给你的信号，不是装饰**：`sandbox_exec` 只要命令里出现 `agent-browser`，返回就带 `browser: {procs, rss_mb}`（服务端 `_browser_procs()` 用 `ps -eo comm=,stat=,rss=` 数 `^(chromium|chrome)` 并排除僵尸进程）。**每次跑完浏览器命令都看一眼这个数字**——它是「会话名churn / close 泄漏」唯一的可观测信号。
- **收到 `browser_hint` ⇒ 立即停手处理**（只有超 **16 procs / 1500 MB** 才会出现）。文案已写明是「第二个会话或泄漏」。处置：`agent-browser --session <你的名字> close`；**同一容器绝不并开第二个会话**；**长扫描（nuclei / sqlmap）之前先 close**，别让浏览器和扫描抢内存。
- **`--session` 不是可选项**：不带 `--session` 会落到默认会话，与同容器其他 agent 互相踩；**`--session` 名字一变就等于新开一个浏览器会话**（procs / RSS 立刻翻倍）。名字在整个容器生命周期内保持一致。
- ⚠ **计数口径陷阱（服务端已修，2026-10-12 w64976）**：本镜像 agent-browser 的引擎进程名是 **`chromium`**（每会话约 13 个），只有 crashpad 助手叫 `chrome_crashpad` ⇒ 自己写进程统计时只匹配 `^chrome` 会**少报约 8×**（实测 2 vs 实际 15）。必须 `chromium|chrome` 都算。
- Run worker streams sequentially or low-concurrency (≤3 concurrent containers); never fan out many heavy processes (host has been exhausted before).

## Engagement gates

- Only test targets the user explicitly authorized (URL/IP range/repo). Confirm scope before any active scanning.
- Prefer non-destructive validation (version banners, reflected input, read-only endpoints) before anything state-changing; `proxy_repeat_request` replays are state-changing — pick safe requests.

### Write-class testing is IN SCOPE (line re-drawn 2026-10-12)

The governing test is **two-axis, not read/write**: a probe is allowed when it is (1) **reversible / self-owned state** and (2) **affects nobody's data or rights**. An earlier codification ("绝对禁止写") was an over-extrapolation of the human ruling and is now retired — under it, arbitrary-file-upload, traversal-write, race condition and IDOR-mutation were permanently untestable, so every "未发现漏洞" in those classes was a coverage lie, not a finding. Test them.

**Human pre-authorization (2026-10-27).** For targets already confirmed in scope, W0, W1 and W2 are pre-authorized. Execute them directly under the four-step discipline and do not ask for another confirmation. W3 and all payment testing remain pending: W3 needs an explicit operator nod in that round, and payment follows the separate L3 authorization path. This pre-authorization does not override credentials, human-notification, scope, volume or cleanup limits.

**Evidence ladder for file upload / traversal-write** (climb in order, stop at the level that settles the rating):

| level | probe | proves | authority |
|---|---|---|---|
| W0 | replay the bypass matrix against **our own** container-side endpoint first (same stack), then send only the 1–3 requests that actually confirm on-target | payload correctness, at our cost | **pre-authorized; always first** |
| W1 | random-named benign `.txt` marker → upload → GET | surface is unfiltered, lands, reachable | **pre-authorized; do not ask** |
| W2 | `<?php echo '<nonce>'; ?>` (or `.jsp`/`.asp` equivalent) → upload → GET shows the literal output, not the source | server **parses/executes** ⇒ 高危 | **pre-authorized; do not ask** |
| W3 | command echo (`id`, nonce) | getshell ⇒ 严重 | **pending; operator nod in that round** |
| ⛔ | real trojan/webshell samples from any malware repo, anything with callbacks, persistent autoload/`.user.ini` pointing outward, cron/startup writes, writing into other apps' directories, anything a third party can see | never — none of this is proof, and it puts the target and us at risk |

**Four-step write discipline (make the wrong state unexpressible).** Every write probe runs all four, in the same round:
1. `GET <planned path>` ⇒ must be **404** (you are not overwriting anyone's file).
2. write, using a nonce name only: `strix-<company_id>-<8hex>.<ext>` — unguessable ⇒ cannot collide, and one-line greppable for the vendor.
3. `GET` ⇒ present and (for W2/W3) executing; keep the raw pair.
4. **delete**, then `GET` ⇒ back to 404. A card missing step 4 is not admissible. If delete is unavailable or fails, do not retry into a loop: register the exact path in `findings/<n>.md` and put a cleanup line in the submission draft so the vendor can remove it in one click. **`rejected`/`blocked_waf`/`no_exec` never landed ⇒ step 4 does not apply** — demanding it there is a false-evidence trap.

State-mutation classes (IDOR 改单/改密/竞态/下单) follow the same rule with objects instead of paths: **only objects this worker created under its own test account, never a third party's id**, and prove the *missing check* rather than completing the business action — where success would be irreversible (password change), stop at the predictable-token/replay evidence, or get operator approval and restore in the same round. Race probes: single target, 2–3 concurrent requests, on a restorable action.

Volume ceilings for write probes: **≤5 per endpoint, ≤10 per target per engagement**, never through a caching/CDN front that amplifies or makes the artifact publicly visible, never on an endpoint that notifies a real person (no 短信/邮件/工单/审核触发).

**Mandatory phase, not an optional trick.** For every authorized target where recon (katana/dirsearch/P6 browsing) reveals **any** upload form/endpoint (`upload`, `file`, `attachment`, `import`, `editor`, `avatar`, `fileinput`, OA/office suites) **or** any file-path-looking parameter (`file=`, `path=`, `doc=`, `download=`, `filename=`, `page=`, `template=`, `redirect=` with a path), running W0→W1→W2 is part of the pipeline, same status as P5 injection testing, and is pre-authorized. Traversal-read (`/etc/passwd`, window equivalents, source disclosure) is likewise a required probe on every file-path parameter — it is zero-harm. `not_tested_by_policy` is no longer acceptable for an otherwise reachable W0–W2 path: only missing credentials, human-notification restrictions, technical/environment blockers, W3 or payment can stop it, and the debt must name the exact stop point. A target with an upload surface and no P7 line in SUMMARY is an incomplete run.

**Untested ≠ safe.** Anything skipped by policy must be recorded as `not_tested_by_policy:<which level, why>`. `ruled_out` requires an actually-executed probe with evidence. A reviewer must be able to tell the three apart.

#### P7 close-out format (single source of truth — a task book that conflicts with it is stale)

⚠ **The machine gate (`scripts/p7_gate.mjs`) is RETIRED** — close-out is now a **self-check against this list**; nothing parses your SUMMARY automatically. The format below is still binding (the panel and the human reviewer read it); it is just no longer regex-enforced.

Worker produces:

1. In `SUMMARY.md`, one line: `P7_STATE: <token>`.
2. If (and only if) at least one write probe was attempted, `raw/P7_manifest.tsv`, one line per probe, tab-separated:
   `<n>\t<outcome>\t<surface>\t<evidence files, comma-separated; bare name or raw/-prefixed both resolve>`
3. Evidence files keep the `P7_<n>_1_pre404 / _2_write / _3_parse / _4_post404` naming (or `_4_cleanup_note.txt` when the endpoint has no delete).

Allowed tokens (three strictly separated states):

| state | tokens | requests | meaning |
|---|---|---|---|
| 确认无写面 | `no_write_surface` / `no_upload_surface` / `no_surface_reachable` | 0 | done — but the P7 section must name the files you judged from |
| **有面但未测（债）** | `surface_requires_credentials` / `needs_credentials` / `not_tested_by_policy` / `blocked_by_env` | 0 或 ≤ 停止点 | **debt** — never counted done, never counted clean; file the debt + the "拿到凭证后的接续四步" instruction in SUMMARY |

Debt outranks no-surface: a section carrying both (e.g. "no *unauthenticated* write surface" **plus** "the upload endpoint exists but needs login") is judged a **debt** — that combination is real. Do not suppress one sentence to make the other win; report both and take the conservative reading.

`policy_stop_w2` is retired for new runs because W2 is now pre-authorized. Keep it only when reading historical summaries produced before 2026-10-27; do not emit it as a new debt.

Per-probe `outcome`: `landed`/`parsed`/`executed`/`reachable`/`landed_no_delete` **must** carry a `_4_post404` or `_4_cleanup_note` (something was written ⇒ closure is not optional); `rejected`/`blocked_waf`/`no_exec` need only the write attempt (+ parse check if made). `needs_credentials`/`not_tested_by_policy` rows need zero files but **must name the surface** — an unnamed debt cannot be handed to a human.

Never fabricate evidence files to satisfy a checklist (a missing `_4` on a probe you never landed is not a defect — record the outcome that actually happened).

Draft coverage applies to **every** path: a target either has `提交库/*_<id>_*.md`, or must declare `no_submit_draft_required:0高中危` **on its own line with no markdown wrapping** (bold-embedded, quoted, or in-sentence forms are wrong). `有 md 无同名 docx` is a WARN, not a defect — human-side renames/packaging are legitimate.
